# 用户模型积累法: 样本 → 分布模型 → 预判验证

## R — Reading (原文)

> "用户模型是指产品用户和潜在用户的偏好和行为反应模型。我们通常把'掌握一个领域的用户模型'视为产品经理的合格线, 掌握的标志是: 预判产品迭代后的用户行为变化, 准确率较高。" (1.3.3)
> "用户每一次行为的单位用户价值是不同的, 要尽可能积累不同用户单次使用体验的样本, 然后在脑子里形成用户分布模型……直到每次做产品决策时, 心里有个判断, 这么想的用户有多少。" (附录·一堂产品课)
> "所谓样本, 就是在具体情境下的每一次使用、每一次反馈或者每一次投诉等。" (2.2.2)

配套: "用户的反馈, 我一字不落; 用户的建议, 我一概不听。" (附录·一堂产品课) / "掌握用户模型这条路没有捷径。" (5.2.1)

## I — Interpretation (自述)

"理解用户"不是读报告, 是建立一个可检验的内部模型: 以"特定情境下的一次使用"为样本单位 (不以自然人为单位——用户是需求的集合), 长期海量地记录、归类每一种用户行为、反馈、评价、bad case 与数据; 样本够多后形成用户分布模型——做决策时心里有"这么想的用户占多少"的判断; 每次迭代前显式写下行为预判, 上线后核对命中率, 持续修正模型。检验标准只有预判准确率。处理口径: 用户的反馈 (发生了什么) 一字不落全部吸收, 用户的建议 (该怎么做) 一概不听——建议没经过专业训练与可行性判断。转岗者 (尤其高职级) 失败率高正是因为跳过了这个积累过程。

## A1 — Application Example (书中案例 / 合成演练)

【书中案例 · firsthand, 出处 5.2.2 与附录史料】俞军 2016 年在知乎阅读 1900 万字 (超过 98% 用户), 加上邮件/微信/全网阅读至少等量——样本积累的日常化; 加入滴滴换领域后"还是在花海量时间重新积累样本"。百度前两年一个人对接所有产品, 网页/MP3/图片/新闻搜索从 0 到 1 的高强度实践即样本积累过程。

【书中案例 · 原书论述, 出处 5.2.1】研发、测试、UI、商业产品、咨询分析等人员转职产品经理不成功, "往往就在于缺乏这个基础积累过程, 尤其转职前职级越高, 转职后管一个团队, 就越不可能花时间重走这个基础积累过程"。

【合成演练 (原书未提供, 按其规则构造)】新任外卖产品经理 90 天计划: 每日记录 5 个样本 (一次点单情境: 反馈/评价/客诉/bad case/自用体验) 按情境归类 → 第 4 周输出初步分布判断 (午晚高峰/恶劣天气/多人餐的诉求占比) → 每次迭代前写预判 ("雨天补贴弹窗点击率将升 X%"), 上线核对 → 命中率入个人月报。反馈全收, 建议仅作参考。

## A2 — Future Trigger (触发情境)

1. 新接手一个产品/领域, 要快速建立用户理解 ("怎么上手懂用户")
2. 团队用户研究只有问卷报告, 决策仍靠拍脑袋
3. 个人成长规划: 判断自己是否具备"合格线"能力
4. 评估转岗/空降产品经理的可行性

语言信号: "用户调研怎么做""怎么真正理解用户""用户画像""样本""预判 / 预测用户行为""客诉分析""bad case" (中英: user research, user model, sample size, predict user behavior, build intuition about users)

与相邻能力的区分 (阶段 3 定稿): 本卡是长期积累程序 (怎么练); 单次行为的机制解释见 user-behavior-mechanism; 无数据时的决策推演 (用模型做什么) 见 decision-method-selection 的主观判断路径。与通用用户调研的区别: 样本单位是"情境×需求"而非人, 检验标准是预判命中率而非报告数量。

**AI 产品化适配** (AI 适配, 非原书) 追加触发情境: ① "让 agent 替我读评价/归类客诉, 算不算积累了用户模型"——采集与初归类可外包, 分布判断不可; ② "AI 聚类出来的用户画像能直接用吗"——警惕按措辞而非情境归类的样本偏差。

## E — Execution (可执行步骤)

输入契约: 一个明确的产品领域 + 可接触的样本源 (反馈渠道/客诉/评价/数据/自用)。无样本源时先开通渠道再谈积累。

1. 定义样本单位: "某类用户在某情境下的一次使用/反馈/投诉" (禁止以"一个用户"为单位笼统记录)。
2. 日常采集 (完成标准: 每日定量, 如 5 条): 来源含自用体验、用户反馈、评价、客诉、bad case、数据异动; 每条记 录情境标签 + 行为 + 推测的期望效用。
3. 归类与分布: 每周按情境×需求归类, 累计后输出分布判断 ("这么想的用户大约多少"), 标注样本量与置信度。
4. 预判-验证闭环: 每次迭代/活动前写显式预判 (可证伪的行为命题), 上线后核对; 记录命中率, 连续低命中说明模型错在哪类情境。
5. 反馈/建议分流: 反馈进样本库全量消化; 建议只登记不采纳 (除非经可行性与价值判断)。
6. 输出: 个人用户模型档案 (分布判断表 + 预判命中记录 + 待补样本类型)。

判停点: 发现自己只在高频场景有把握、长尾情境全靠猜 → 该情境标记"模型未覆盖", 决策时显式降置信度, 不硬给结论。

输出契约: 持续更新的样本库 + 分布判断表 + 预判命中率记录; 完成标准 = 预判有记录且可回查, 分布判断带样本量。

**AI 产品化适配** 要点 (AI 适配, 非原书):
1. agent 可承包采集与初归类 (批量读评价/客诉并打情境标签), 但每周的分布判断 ("这么想的用户占多少") 必须人写——量级感是模型本身, 不可外包。
2. 防 AI 归类样本偏差 (可核验): AI 聚类倾向按表面措辞而非"情境×需求"归类; 抽 10% 人工复核, 归错超三成即改回人工归类。
3. 预判-验证闭环不省略: 可用 agent 生成预判候选清单, 上线核对命中率与修正模型仍由人执行并记录。
4. "反馈一字不落"口径对 AI 汇总同样适用: AI 摘要会抹平 bad case 细节, 每周保留一定量原始反馈直读, 不全靠摘要。
5. 完成标准: 样本库每条标注采集方式 (人读 / AI 归类+复核状态), 预判命中率记录持续存在。

## B — Boundary (边界)

- 没有捷径、不可速成: 作者明言这条路没有捷径; 90 天演练只是起步, "对于大多数单一产品的产品经理, 仅做这一件事就需要三五年时间"。本卡给的是程序, 不承诺速成。
- 用户模型强领域绑定: 换领域基本重来 (俞军自己到滴滴也重新积累); 跨领域迁移的只有"智慧等级"式的思维框架, 不是模型本身。
- 预判检验受迭代速度约束: 低频迭代产品 (硬件一年一版) 验证机会少, 积累效率天然低——选成长环境时需考虑 (见 pm-growth-path)。
- "建议一概不听"是处理输入的口径不是傲慢: 建议背后的事实 (为什么不满意) 仍要全部吸收。
- 作者盲点提醒: 该方法论默认能触达海量反馈 (大平台); 小用户量产品的样本积累要靠深度访谈与行业 bad case 池补充, 密度不同。
- 相邻易混: 单次行为机制分析见 user-behavior-mechanism; 问卷与画像工具不在本卡范围 (作者对问卷口径的批评见 ce07/ce20)。
- **AI 产品化适配** (AI 适配, 非原书): 不要把"agent 读完了全部反馈"等价于"我积累了用户模型"——合格线是预判命中率, 不是处理量; AI 汇总的平滑与抽样会系统性抹掉长尾 bad case, 恰是样本里最值钱的部分。
